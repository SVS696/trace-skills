# Этапы разработки

Начни с `spec_ready`. Выполни [проверку OpenSpec](openspec.md) и выбери маршрут.

```bash
python3 scripts/caseflow.py route --case-root CASE --decision delivery \
  --lane BACKEND --lane FRONTEND --lane TEST \
  --openspec-root /absolute/planning-repo --openspec-change CHANGE
```

Перед назначением или возобновлением работы запроси `caseflow.py context --case-root CASE --lane BACKEND` для нужного участка. Исполнитель получает проверенную статью, текущие зарегистрированные результаты участка и интеграцию предыдущего этапа разработки. Черновики блоков постановки остаются вне его активного контекста.

На каждом этапе зарегистрируй через `delivery-submit` один результат и методическую основу для каждого объявленного участка. Затем используй `delivery-open-stitch` и `delivery-record-stitch`. Обрабатывай пункты одного списка этапа через `delivery-resolve`, `delivery-verify --result pass|fail` или `delivery-waive --decision-ref`. Для нового дефекта вызови `delivery-append-item --item-file`. Не редактируй список вручную. После закрытия списка вызови `delivery-advance`. Для продолжения прерванной работы прочитай `caseflow.py status`.

## Этап 1. План

Входы — утверждённая статья, привязанный пакет OpenSpec и маршрут `delivery`.

1. Распредели задачи OpenSpec по номерам между исполнителями сервера, клиента и тестов. Для каждого участка укажи файлы, требования, согласованную `solution_boundary` и проверки. Укажи ответственный путь на каждом шаге перехода, вывод прежнего пути и применимые условия отката.
2. Сведи планы по API, зависимостям, владельцам и общим файлам. Для каждой гарантии между слоями определи ответственный слой, обязанности потребителя, направление данных и отдельные проверки BE/FE/E2E.
3. Для нескольких репозиториев по [правилам передачи](../../../rules/handoff-contract.md) подготовь набор SHA, совместимость смешанных версий поставщика и потребителя, общую сборку и среду. Укажи миграции, флаги, порядок слияния и развёртывания, откат.
4. Закрой общий список замечаний к плану до изменения кода. Проверь, что исполнители могут начать работу по совместимым контрактам.

## Этап 2. Реализация

Начни после закрытия списка этапа 1.

1. Выполни назначенные задачи и тесты разработчика. Верни сведения по каждой задаче. Ведущий сверяет результат и обновляет общий список задач.
2. Объедини изменения. Выполни сборку, тесты и статические проверки обычными инструментами. Исправь ошибки. Зафиксируй точный diff. Отдельный `quality-pass-reviewer` применяет `simplicity-code` к этой версии. Привяжи [отчёт](../../../rules/quality-pass.md) к diff и точным байтам скилла.
3. После правок, до следующего вызова модели, повтори автоматические проверки. В единый список этапа внеси принятые замечания по простоте и оставшиеся дефекты. Зарегистрируй его через `delivery-record-stitch --simplicity-report ...`. Сохрани минимальные обязательные гарантии решения.
4. Внеси только зарегистрированные исправления. Повтори те же проверки. Передай общую версию с успешными проверками разработчика и результатом `simplicity-code`, в том числе если упростить ничего не потребовалось.

## Этап 3. Независимая проверка

Начни после успешных проверок общей версии разработчиком.

1. Независимый проверяющий сопоставляет согласованную статью с пакетом OpenSpec, требования и задачи — с кодом и тестами. Проверяет фактическую реализацию по каждой отметке в списке.
2. Проверь соответствие проекту и регрессию с учётом риска. Проверь гарантии поставщика непосредственно, поведение потребителя отдельно, затем их взаимодействие в E2E. Аналитическое и кодовое ревью дополняют проверку поведения QA на известной сборке и в указанной среде.
3. Для нескольких репозиториев используй точный совместный набор SHA. При изменении компонента повтори затронутые проверки новой комбинации. Если общая сборка недоступна, оставь совместную проверку открытой.
4. При использовании revmux передай замечания независимому исполнителю `simplicity-code`, для документа — `simplicity-spec`. Принятые замечания собери в одном списке. Для отклонённых укажи основание. Исправь пункты списка, выполни автоматические проверки и перепроверь изменённые участки и затронутые классы с необходимыми источниками. Действуют предел пяти содержательных раундов и остановка при одних мелких замечаниях. Покажи остаток явно. Если revmux не применялся, собери подтверждённые дефекты в одном списке и перепроверь точный diff исправлений.

Выход — независимые результаты без блокирующих дефектов. Храни отчёты разработчика и проверяющего отдельно.

## Этап 4. Передача

Начни после закрытия списка этапа 3.

1. По [правилам передачи](../../../rules/handoff-contract.md) укажи получателя, нормативные версии, коммит, MR, тесты, изменение OpenSpec и подтверждения по задачам. Сопоставь критерии со свидетельствами. Отметь открытые вопросы и условия следующего действия.
2. Отдельно проверь и сообщи, выполнены ли слияние, развёртывание и приёмка. Если развёртывание входит в поручение, сверь фактическую версию с проверенным набором.
3. Выполняй внешнюю запись только с нужными полномочиями. Прочитай записанный результат и сверь его с ожидаемым. Передай отчёт, ограниченный подтверждёнными сведениями.
