# Предварительная записка

Для нового `preanalysis-brief.json` используй схему 4. Валидатор читает схемы 1–3 для начатых кейсов. Для нового кейса `caseflow init` принимает только схему 4.

## Вопросы до выбора маршрута

Ответь на четыре вопроса независимо от заголовков будущей статьи.

1. Кто, в каком сценарии и с какой трудностью сталкивается? Какое отрицательное последствие это вызывает?
2. Кто должен получить наблюдаемый результат и какую пользу он принесёт?
3. Как изменится поведение процесса или системы и почему это устранит проблему?
4. Какому участнику нужна какая возможность и для чего?

Для ответа дай ссылку на источник. Укажи причину и следствие. Название компонента, перечень доработок и термин без объяснения роли в сценарии недостаточны. Если имеющиеся сведения не позволяют ответить и ответ меняет объём, верни `gap`. Классифицируй пробел и задай точный вопрос до выбора маршрута.

## Состав записи

| Поле | Что записать |
|---|---|
| `subject_id` | Постоянный идентификатор предмета |
| `sources` | Для каждого источника укажи `id`, `kind`, `ref`, точный `query`, `authority`, `status=found\|negative\|unavailable`, `checked_at` в формате ISO и `freshness=current\|stale\|unknown` |
| `facts`, `contradictions` | Факты и противоречия со ссылками. Для разрешённого противоречия укажи решение |
| `coverage` | `verdict=sufficient\|partial\|blocked`, непустой список проверенных областей. Для непокрытой области укажи идентификаторы неизвестных в `gap_refs` |
| `problem` | `statement`, непустые `affected_actors`, `negative_consequences` и `evidence_refs` |
| `goal` | `statement`, непустые `beneficiaries`, `benefits` и `evidence_refs` |
| `solution_essence` | `statement`, непустые `behavior_changes`, `problem_resolution`, `evidence_refs`. Объясни, почему изменение устраняет проблему. Неопределённость отрази в источниках, допущениях и открытых вопросах |
| `solution_boundary`, `architecture_gate` | [Граница и переход](../../../rules/solution-boundary.md), [архитектурные условия](../../../rules/architecture-analysis.md) |
| `preliminary_user_stories` | Как минимум одна история. Для каждой нужны `id`, `actor`, `need`, `value`, непустой `evidence_refs` и `confidence=low\|medium\|high` |
| `preliminary_definition_of_done` | Для каждого критерия нужны `id`, `criterion`, наблюдаемое `evidence`, непустой `evidence_refs` и `confidence` |
| `scope_in`, `scope_out`, `unknowns`, `assumptions`, `dependencies` | Массивы включённого и исключённого объёма, неизвестных, допущений и зависимостей |
| `estimate` | Диапазон прогноза и его основание либо причина отсутствия оценки |

### Границы решения

Пример описывает условную задачу. Для рабочего решения нужны сведения проекта.

```json
{
  "horizon": "bounded-systemic",
  "observed_case": "При пустом названии пользователь получает общее сообщение об ошибке сохранения.",
  "root_capability": "Пользователь сохраняет черновик сценария.",
  "invariants": ["Сервис сценариев проверяет обязательные поля."],
  "confirmed_variants": [
    {"name": "Сохранение черновика с пустым названием", "evidence_refs": ["SRC-001"]}
  ],
  "hypothesized_variants": [],
  "current_scope": ["Если название пустое, форма указывает поле, которое нужно заполнить."],
  "extension_seams": ["Форма использует существующее сопоставление кода ошибки и поля."],
  "extension_seam_absence_reason": null,
  "deferred_variants": [],
  "expansion_triggers": ["Появился второй подтверждённый потребитель сведений об ошибке."],
  "horizon_evidence": {
    "analogy_search_refs": ["SRC-001"],
    "roadmap_refs": [],
    "irreversibility_refs": []
  },
  "hotfix_exception": null,
  "implementation_transition": {
    "status": "selected",
    "mode": "evolve-in-place",
    "authoritative_owner": "scenario-service",
    "superseded_paths": [],
    "coexistence_reason": null,
    "stages": [],
    "retirement_trigger": null,
    "rollback_boundary": null,
    "evidence_refs": ["SRC-001"],
    "reason": "Сервис уже возвращает ошибку проверки названия."
  }
}
```

Для каждого подтверждённого варианта дай минимум одну ссылку на источник. Заполни `invariants`, `current_scope` и `expansion_triggers`. Если `extension_seams` пуст, обоснуй это в `extension_seam_absence_reason`. Предполагаемые и отложенные варианты сами по себе не входят в текущий объём.

Для `tactical` заполни `hotfix_exception` непустыми `reason`, `reversibility`, `return_trigger`, `evidence_refs`. Для других горизонтов используй `null`. Для `generalized-capability` нужны как минимум два подтверждённых варианта, план развития со ссылкой или свидетельство дорогой либо необратимой переделки. Для обычной задачи обоснуй `bounded-systemic` на установленных границах.

В записке опиши задачу целиком. В решении по схеме 3 задай границу каждой статьи. Для `single` перенеси границу из записки. Изменить её можно по явно зафиксированным новым сведениям. Для `split` обоснуй границы отдельных статей по тому же списку источников. Горизонты разных статей могут различаться.

Для `implementation_transition` выбери `not-applicable` или `selected`. Во втором случае укажи `evolve-in-place`, `replace-and-remove` или `staged-migration`. Для замены и поэтапного перехода назови прежние пути, условие вывода и границу отката. Для поэтапного перехода обоснуй одновременную работу путей и укажи одного ответственного на каждом этапе. Добавляй новые бизнес-правила только в ответственный путь.

Если архитектура требует проверки, укажи `architecture_gate.status=required` и точные условия из архитектурного контракта. Для `not-required` оставь список условий пустым и объясни причину. Для `tactical` и `generalized-capability` архитектурная проверка обязательна.

### Покрытие, вопросы и оценка

Выбирай `sufficient` только при полном покрытии всех заявленных областей. Затем закончи широкий поиск. Для нового поиска нужны конкретный вопрос, источник и условие остановки.

Для каждого элемента `unknowns` заполни `id`, `statement`, `disposition`, `blocks_specification` и `reason`. Выбери один вариант:

- `researchable` — продолжи сбор сведений. Пробел блокирует постановку.
- `user-decision` — укажи точный `question` и задай его пользователю. Вопрос блокирует постановку.
- `external-owner` — укажи `owner_ref` владельца сведений. Если ответ блокирует подготовку статьи, перенеси вопрос в `open_inputs` первого затронутого этапа. Включи ответ до готовности.
- `implementation-only` — обоснуй, что ответ не меняет наблюдаемые требования, сценарии или AC. Такой вопрос не блокирует постановку.

Для оценки выбери одну форму.

```json
{"status":"estimated","min":3,"max":6,"unit":"working_days","confidence":"low","basis":["source-or-assumption"]}
```

```json
{"status":"unavailable","reason":"Для оценки не хватает данных о затронутых компонентах."}
```

Оценка описывает прогноз. Срок обязательства и фактическое время фиксируй отдельно.
