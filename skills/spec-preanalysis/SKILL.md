# Предварительный анализ постановки

Начни с описания задачи и текущего шаблона. Прочитай [правила TRACE](../../rules/process-kernel.md) и [правила языка](../../rules/technical-writing.md). Предварительный анализ нужен, чтобы определить объём, число независимо принимаемых результатов и план статьи. Для небольшой правки известной статьи или неизменившегося согласованного решения повторный анализ не требуется. Для старого кейса сначала проведи инвентаризацию через `legacy-case-migration`. Для реализации по `spec_ready` используй `delivery-workflow`.

## 1. Собрать основания

1. Составь список источников. Для каждого поиска запиши точный запрос, полномочия источника, время, актуальность и результат `found|negative|unavailable`. Различай факты, допущения и противоречия. Отметь покрытие по каждому предмету проверки. После `sufficient` закончи широкий поиск. Вернись к нему для конкретного пробела или вопроса, который может опровергнуть вывод.
2. Через `method-library` подготовь нужный маршрут требований, обычно `scope-users` или `elicitation`. Передай путь и хеш роли `spec-preanalyst`. Передай ей источники и инструкцию языкового скилла для режима написания. Русские предварительные истории и критерии готовности формулируй сразу на УТР, английские — на упрощённом техническом английском.
3. До выбора числа статей ответь на четыре вопроса из [правил записки](references/brief-contract.md). Кто сталкивается с какой проблемой и к чему она приводит? Какой результат нужен и кому он принесёт пользу? Как изменится поведение и почему это решит проблему? Кому нужна какая возможность и для чего? Последний ответ запиши как предварительную историю пользователя. Все четыре части нужны независимо от заголовков шаблона. Сформулируй суть решения отдельным утверждением. Объясни причинную связь изменения с проблемой. Приведи источник для каждого ответа, в том числе для связи решения с проблемой. Для существенного пробела запиши точный вопрос.
4. Для каждой предварительной истории и критерия готовности (DoD) укажи источник и уверенность. Для каждого неизвестного выбери одно действие. Продолжи поиск, задай вопрос пользователю, подготовь точный запрос внешнему владельцу сведений и отправь его при наличии полномочий или обоснуй, что ответ относится только к реализации.
5. Примени [правила границ решения](../../rules/solution-boundary.md). Определи базовую возможность, её инварианты, подтверждённые и предполагаемые варианты. Запиши текущий объём, место расширения или причину его отсутствия, отложенные варианты и условия пересмотра. Обоснуй горизонт `tactical`, `bounded-systemic` или `generalized-capability`. Основной выбор для обычной задачи — `bounded-systemic`. Выбери переход `evolve-in-place|replace-and-remove|staged-migration` либо обоснуй неприменимость. Передай `spec-preanalyst` путь и хеш контракта.
6. Проверь [архитектурные условия](../../rules/architecture-analysis.md). Если хотя бы одно выполнено, до согласования назначь новый запуск `spec-solution-architect`. Привяжи путь и хеш проекта решения к каждой затронутой статье. Иначе запиши `not-required` и причину.
7. Примени `simplicity-spec` к сути решения и предложенному составу работ. Удали или отложи механизмы без текущего требования. Сохрани минимальные необходимые гарантии и обоснованное место расширения.
8. Запиши упрощённое решение в `preanalysis-brief.json` по схеме 4. Добавь диапазон оценки, основание и уверенность либо причину отсутствия оценки. Фактическое время учитывает `process-timer`. Выполни `scripts/preanalysis.py validate-brief`. Каждый пробел должен иметь назначенное действие.

## 2. Определить число статей

После проверки записки примени [критерии разделения](references/routing-criteria.md). Предложи `single`, если результаты нельзя принять и передать независимо без копирования общих правил. Для `split` выдели общие сведения один раз. Покажи зависимости без циклов. Для каждой статьи установи свою цель, результат, границу приёмки и подтверждённую границу решения. Сервер, клиент, экран, команда или число исполнителей сами по себе не определяют число статей.

## 3. Выбрать смысловые блоки

Для каждой статьи запиши `composition: article-led`. На первом этапе автор готовит полный рабочий текст по выбранному шаблону. Затем он уточняет один или несколько блоков. Выделяй блок по сценарию, риску, группе правил, жизненному циклу данных или интерфейсу. Если первый полный текст выявил ошибку в границах блока, оформи новое решение о составе работ перед переназначением исполнителей.

## 4. Согласовать решение и план

1. Подготовь `decomposition-decision.json` по [схеме 3](references/decision-contract.md). Укажи границу решения каждой статьи.
2. Подготовь `execution-plan.json` по [схеме 2](references/plan-contract.md). Привяжи план к хешу записки. Проверь, что зависимости задач в плане не образуют циклов. Для каждой задачи назови продуктовый результат, укажи источники и наблюдаемый признак завершения. Для номеров этапов, идентификаторов и операций TRACE используй отдельные поля.
3. Проверь все три документа. Представь пользователю проблему, цель, суть решения, предварительные истории, оценку, план, существенные компромиссы и результат `simplicity-spec`. До согласования задай все прямые вопросы `user-decision`, которые меняют эти ответы, границы, число статей или приёмку.
4. После ответа пользователя запиши согласование решения и плана с точным `decision_ref`. Ведущий агент отвечает за проверку документов, разбор вариантов и запись решений. Если пользователь разрешил внешнюю синхронизацию, опубликуй план через адаптер проекта (например, `singularity-app`). Прочитай результат и зафиксируй подтверждение.
5. Только после согласования создай каждый кейс через `caseflow.py init --brief ...`. Зафиксируй записку, решение, план и применимый архитектурный проект как неизменяемые входы. Открытый вопрос, влияющий на содержание, перенеси в `open_inputs` первого затронутого этапа до разрешения. На этапе 1 каждая предварительная история и каждый DoD должны получить итоговую ссылку и решение.

Результат этапа — проверенная записка, согласованное решение и план. Написание итоговой статьи выполняет `spec-workflow`.
