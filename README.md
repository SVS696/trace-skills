# TRACE

**Traceable Requirements Analysis, Composition & Engineering**

TRACE помогает провести исследование, подготовить постановку и передать согласованную работу в разработку. Метод объединяет правила Vigers и Delivery Engineering, роли исполнителей, журнал времени и средства проверки.

## Выберите результат

| Что требуется | С чего начать | Что получит следующий участник |
|---|---|---|
| Ответить на вопрос или сравнить решения | `analysis-workflow` | Вывод с источниками и границами применимости |
| Определить, какую задачу решать | `spec-preanalysis` | Описание проблемы, цели и решения, предварительные пользовательские истории, критерии готовности, оценку, план и решение о числе постановок |
| Подготовить согласованную по объёму постановку | `spec-workflow` | Статью по шаблону основной постановки или компонентной подзадачи |
| Реализовать согласованное изменение | `delivery-workflow` | Изменение кода, результаты проверок разработчика и независимой проверки |
| Продолжить незавершённый кейс старого процесса | `legacy-case-migration` | Пересмотр прежних материалов и основание для нового кейса |

Проект задаёт источники, шаблоны и порядок публикации. При передаче работы укажите версию результата и проверки, которые выполнил участник. [Контракт передачи](rules/handoff-contract.md)

## Как подготовить постановку

1. Проверьте источники. Опишите проблему, ожидаемую пользу, границы и план. Получите решение пользователя по материалам преданализа.
2. Пишите постановку сразу по источникам на УТР, а для английского результата — на упрощённом техническом английском. Заполните все применимые разделы шаблона. Укажите, что произошло с каждой предварительной пользовательской историей и каждым критерием готовности. Включите только компоненты, которые меняет задача.
3. Уточните поведение и условия приёмки. После каждой стадии сохраните новую целую версию статьи. Передайте на проверку итоговую статью четвёртой стадии.
4. Запустите независимое ревью в `revmux`. По принятым замечаниям составьте единый список исправлений. Исправьте статью и передайте обновлённую версию на следующий обычный раунд. До первого ревью автор правит черновик напрямую.
5. Завершите ревью при чистом результате. Если остались только мелкие замечания, перечислите их. После пяти содержательных раундов с открытыми замечаниями дальнейшую работу определяет пользователь.

## Язык постановок и документации

Для русского текста используйте `$utr`, для английского — `$simplified-technical-english`. Установите нужный скилл из личного каталога SVS. В комплект каждого входят правила, словарь и примеры. Чтобы проверить редакцию, передайте исходник и новый текст. ## Запуск

Из корня установленного репозитория создайте кейс по утверждённым материалам. Замените пути в примере путями своего проекта.

```bash
python3 scripts/caseflow.py init \
  --case-root .workflow/cases/CASE-123 \
  --template /absolute/path/to/current-template.md \
  --brief /absolute/path/to/preanalysis-brief.json \
  --decision /absolute/path/to/decomposition-decision.json \
  --plan /absolute/path/to/execution-plan.json \
  --article-id CASE-123

python3 scripts/caseflow.py status --case-root .workflow/cases/CASE-123
python3 scripts/caseflow.py context --case-root .workflow/cases/CASE-123
```

Команда `status` показывает состояние кейса. Команда `context` перечисляет материалы для текущей стадии. Передайте исполнителю источники из этого списка.

Для новой разработки установите Node.js версии 20.19.0 или выше и OpenSpec версии от 1.13.0 до 2.0.0, не включая 2.0.0. Команда ниже устанавливает проверенную версию. Анализ и подготовка статьи работают без OpenSpec.

```bash
npm install -g @fission-ai/openspec@1.13.0
python3 scripts/openspec_bridge.py
```

Для интеграции проекта с Codex и Claude Code используйте `openspec init --tools codex,claude`. Свяжите пакет изменения с проверенной версией статьи. TRACE повторно проверяет пакет при запросе контекста и переходе на следующую стадию. Отдельно зафиксируйте разработку, результаты тестов, публикацию, слияние, развёртывание и приёмку. [Порядок установки](docs/adoption.md) · [Вход в разработку](skills/delivery-workflow/references/openspec.md)

## Инструменты

- `method-library` выбирает методические правила для текущей работы. Их источники, версии и контрольные суммы хранятся в `library/`. [Происхождение правил](docs/rule-preservation.md)
- `scripts/caseflow.py` проверяет переходы между стадиями и учитывает замечания. `process-timer` и `scripts/work_timer.py` записывают события для Work Metrics. Журнал пополняется по мере работы.
- В `agents/` описаны полномочия отдельных исполнителей. Общие правила собраны в `rules/process-kernel.md`. Для проверки простоты и языка TRACE вызывает `simplicity-spec`, `simplicity-code` или `humanizer` в соответствующей точке работы. Каждый проход оставляет один отчёт. [Правила отчёта](rules/quality-pass.md)
- Smoke Break напоминает проверить ход длительной работы по правилу `P23 COURSE-CHECK`. Для Codex используйте исходный плагин. Для Claude Code репозиторий содержит адаптер. TRACE рекомендует интервал 15 минут. Укажите его в `~/.smoke-break.env`. Команда `python3 scripts/smoke_break_dependency.py verify` проверяет установку. Если плагин отсутствует, остальные проверки остаются доступны. [Исходный плагин](https://github.com/ElKornacio/agent-plugins/tree/511e18062c95d746bed7ff0ca300fbcbd31fc57f/plugins/smoke-break) · [Адаптер](integrations/smoke-break/README.md)

## История решений

TRACE сохраняет методические правила предшественников и историю их версий. Для совместимости с установленными агентами и открытыми кейсами используется путь `~/.workflow-skills/current`. Локальные несогласованные изменения Vigers хранятся в архивной рабочей копии.
