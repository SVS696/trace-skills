# Как писать требования и инструкции

Пишите постановки и техническую документацию по-русски на упрощённом техническом русском (УТР). Для английских документов используйте Simplified Technical English и приёмы IBM EasyEnglish. Применяйте тот же подход к инструкциям новых скиллов. Сохраняйте язык, который выбрал проект или заказчик.

## Русский текст

1. Начните требование с условия, если оно есть. Назовите исполнителя, действие и объект. Укажите ограничение или наблюдаемый результат там, где он влияет на поведение.
2. Разделите требования, которые можно проверить по отдельности. Если несколько действий составляют одну атомарную операцию, укажите это явно. Сохраните порядок действий, область отрицания и связь между условиями «и» и «или».
3. Используйте один термин для одного понятия. При первом употреблении поясните проектное сокращение. Переносите имена полей, статусы, названия кнопок, единицы измерения и команды из источника точно.
4. Указывайте силу требования. «Должен» обозначает обязанность. «Может» требует ясного контекста: назовите разрешение или опишите возможность. Право пользователя удобно передать словом «вправе». В описании наблюдения укажите источник факта.
5. В шаге инструкции начните с глагола. В критерии приёмки укажите начальное состояние, действие и результат, который можно проверить. В описании архитектуры сохраните причину решения и условия, при которых оно действует.
6. Проверьте альтернативы и ошибки по источнику. Если срок, получатель, права или поведение при ошибке неизвестны, запишите открытый вопрос. Если решение принимает конкретный человек, укажите его рядом с вопросом. Запишите каждый пробел один раз.

Ориентир для процедурного шага — короткое предложение про одно действие. В требованиях длину определяет смысл. В таблицу удобно вынести несколько сочетаний условий и результатов. Для пояснения к схеме или API используйте те же правила. Синтаксис схемы и контракт API задаёт проект.

**Пример.** Источник требует, чтобы при повторной отправке заявки сервис вернул идентификатор исходной заявки. В постановке можно записать: «Если клиент повторно отправляет ту же заявку, сервис возвращает идентификатор исходной заявки». Если источник не определяет признак повтора, спросите, как сервис распознаёт ту же заявку. До решения оставьте этот вопрос открытым.

Русский профиль TRACE использует принципы раздела 8.2 ГОСТ Р 58049-2017. Для управления требованиями используйте применимые рекомендации ГОСТ Р 59194-2020. Если проект готовит ТЗ на автоматизированную систему по ГОСТ 34.602-2020, сверьте с ним состав документа. Применение профиля само по себе не подтверждает соответствие документа стандарту. [ГОСТ Р 58049-2017](https://protect.gost.ru/gost/details/4183a5cf-a3af-4e95-97bd-c7bb4bb27063), [ГОСТ Р 59194-2020](https://protect.gost.ru/gost/details/715dcbac-76d6-481a-bd29-8037680321c6), [ГОСТ 34.602-2020](https://protect.gost.ru/gost/details/5876f733-ee91-431a-8cb6-9e02ea2436ac).

## English documents and skills

Use one term for each concept. Keep the project's technical nouns and verbs. Copy identifiers exactly. Start a procedure step with a verb. Put a condition before the action it controls. In descriptive text, name the component that performs the action. Distinguish permission from obligation. If a decision is pending, name its owner beside the open question. Ask once about each gap. Use the ASD-STE100 rules for the type of text you write. Use the IBM EasyEnglish approach to find ambiguous pronouns, long noun groups, and sentences that allow two readings. This is an adapted writing profile. A claim of full STE compliance requires a separate check against the standard. [ASD-STE100](https://www.asd-ste100.org/about_STE.html), [IBM EasyEnglish](https://research.ibm.com/publications/easyenglish-a-tool-for-improving-document-quality).

Select an extension that fits the document:

- **System requirements.** Use the project's requirements method. ISO/IEC/IEEE 29148 provides guidance for requirements engineering. An EARS pattern can make a trigger or state explicit. For example, “When the client submits the same request again, the service shall return the original request ID.” Define how the service identifies the same request. Keep that question open if the source gives no rule. [ISO/IEC/IEEE 29148](https://www.iso.org/standard/72089.html), [EARS](https://alistairmavin.com/ears/).
- **Protocol specifications.** If the document adopts BCP 14, use its uppercase keywords with their defined meanings. Keep the project's convention in other documents. [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).
- **Skills and procedures.** Name the input, action, output, and completion condition. Put each exception beside the step it changes. Example: “Read the receipt. If its hash differs from the article hash, report the mismatch and stop before publication.”

## В каком порядке применять скиллы

1. Пишите черновик сразу на языке документа. Оставьте читателю причину правила, если она есть в источнике. Отделите её от обязательного поведения.
2. Если проект требует `humanizer` или читатель теряет смысл за формулировками, примените его к черновику. Назовите читателя и его задачу. Переставляйте пояснения, убирайте повторы, объединяйте связанные условия. В требовании технический термин может повторяться для точности. Если фраза уже ясна, сохраните её. Для короткого технического правила без проблем чтения достаточно языковой проверки, если проект не требует отдельного прохода.
3. После последней редакторской правки дайте исходник и исправленные фрагменты скиллу `utr` или `simplified-technical-english` в режиме проверки. Сверьте обязательность, роли, связи между условиями, исключения и технические обозначения. Проверьте, осталась ли причина правила связанной с тем же сценарием. Исправьте подтверждённые расхождения и перечитайте изменённые строки. Если текст допускает два поведения, сохраните вопрос к владельцу решения.
4. Проверьте, сможет ли читатель применить правило. Например, попросите назвать, кто вправе повторить операцию, что произойдёт на границе допустимого значения и какой случай ещё не определён. Ответы должны следовать из готового текста и совпадать с источником. Для короткого правила достаточно штатного примера и существенного исключения, если оно есть. Для инструкции проверьте, найдёт ли исполнитель следующее действие и условие остановки.

В TRACE автор выполняет эту сверку в текущей стадии. Назначенный проверяющий оценивает понятность и смысл той же версии в обычном раунде ревью. Скилл `copywriting` выбирайте для отдельно запрошенного рекламного или продуктового текста с целью убеждения. Если такой текст цитирует техническое обещание, сверьте обещание с первоисточником.

## Проверка при редактуре

Сравните новую формулировку с источником. Проверьте, остались ли те же исполнитель, условие, обязательность, результат и исключения. Проверьте значимые числа и идентификаторы. Если две трактовки всё ещё возможны, назовите обе и укажите, какое решение требуется. Выполните эту проверку при обычной редактуре текста.
