# Общие правила TRACE

Ведущий агент читает эти правила один раз для задачи. Каждому исполнителю передай только те правила, которые относятся к его заданию. Правила сохраняют применимые методы Vigers и Delivery Engineering.

## Источники и решения

- `P01 SOURCE-ORDER`. Учитывай явный запрос, правила проекта и актуальные источники прежде общей методики. Если они противоречат друг другу, укажи противоречие.
- `P02 NO-INVENTION`. Подтверждай требования, интерфейс, данные, владельцев, сроки, статусы и внешние факты источником. Если сведений мало, обозначь гипотезу, допущение или пробел.
- `P03 EVIDENCE-TYPES`. Различай факт со ссылкой, интерпретацию, гипотезу, допущение, противоречие и неизвестное. Меняй статус утверждения, когда появилось основание.
- `P04 SOLUTION-BOUNDARY`. Определи, какую общую потребность показывает частный запрос. Включи в решение подтверждённый объём. Сохрани минимальное место расширения, если источники подтверждают общий класс задач или дорогую необратимую переделку. Выбери `tactical|bounded-systemic|generalized-capability` по [правилам границ](solution-boundary.md). Отдельно проверь `particular-case` и `speculative-generalization`.
- `P05 DECOMPOSITION`. Сначала определи число независимо принимаемых результатов. Для каждого подготовь полную статью по шаблону. Затем уточняй её по смысловым блокам. Наличие серверной и клиентской частей, отдельных экранов или исполнителей само по себе недостаточно для разделения.

## Постановка и читатель

- `P06 TRACEABILITY`. Свяжи источник и цель с требованием, сценарием и критерием приёмки прямыми ссылками. Достаточно ссылок, по которым читатель может пройти эту цепочку.
- `P07 READER-PROJECTION`. В публичной статье опиши предмет задачи по [правилам технического языка](technical-writing.md). Определи каждый факт один раз. Внутренние идентификаторы процесса, рассуждения, замечания и статусы проверок оставь в рабочих материалах.
- `P08 TEMPLATE`. Во время подготовки статьи сохраняй исходный проектный шаблон и его контрольную сумму. Заполни весь применимый шаблон до задания отдельных блоков. На каждом последующем этапе уточняй уже существующий полный текст.
- `P09 AC-DOD`. Критерий приёмки (AC) описывает входное условие и ожидаемый наблюдаемый результат. Критерий готовности (DoD) показывает, когда результат можно передать на приёмку. Записывай самопроверку разработчика отдельно. Её результат сам по себе не подтверждает выполнение AC или DoD.

## Исправления и статус

- `P10 EXACT-DIFF`. До revmux автор и редактор исправляют статью напрямую, в том числе по результатам автоматических проверок. После revmux создай один список принятых замечаний. Внеси каждую правку в итоговую статью и при необходимости в промежуточный файл. Зарегистрируй применение. Следующий обычный раунд revmux проверяет обновлённую статью. Отдельная точечная проверка для постановки не нужна. Старые поэтапные списки поддерживаются для совместимости. Для реализации действует свой контракт.
- `P11 INDEPENDENCE`. Автор проверяет свою работу. Независимое заключение даёт другая роль или модель по точной текущей версии и собственным свидетельствам.
- `P12 HONEST-STATUS`. Для `draft`, `reviewed`, `approved`, `handed off`, `committed`, `merged`, `deployed` и `accepted` нужны отдельные основания. Успех локальной проверки подтверждает только её результат.
- `P13 EXTERNAL-WRITE`. Для публикации, смены статуса в трекере, слияния и развёртывания нужны соответствующие полномочия. После разрешённой записи прочитай результат и сравни с ожидаемым.
- `P14 PROJECT-OWNERSHIP`. Проект определяет источники, архитектуру, шаблоны, способы публикации и внешние статусы. TRACE задаёт порядок работы. Определи маршрут, версии, владельцев решений и входы получателя по [правилам передачи](handoff-contract.md). Оставь доступные проектные ссылки на решения. Для новой реализации в Codex и Claude Code примени [правила OpenSpec](../skills/delivery-workflow/references/openspec.md). Нормативным остаётся источник проекта.
- `P15 BOUNDED-CONTEXT`. Передай модели общие применимые правила, один текущий этап или маршрут, предмет задания и активные изменения. Из каталога инструкций выбери документ по идентификатору, сверь версию контракта и хеш текста. Факты о текущем состоянии проверяй в проекте. Полные книги, закрытые замечания и чужие участки работы исключи из задания.
- `P16 IMPACT-RECHECK`. После исправления постановки запусти обычный revmux по новой статье. Сохрани проектные критерии и источники принятых замечаний. Автоматические проверки подтверждают целостность файлов. Смысл проверяет ревью. Для изменения объёма или горизонта получи явное решение.
- `P17 PRACTICAL-RISK`. Перед исправлением проверь, достижима ли проблема в штатном сценарии. Оцени вероятность, ущерб и сложность исправления. После полного revmux примени `simplicity-spec` для постановки или `simplicity-code` для реализации к полученным замечаниям. Для подтверждённых замечаний выбери минимальную соразмерную правку. Для остальных сохрани основание отклонения. Оценка серьёзности, безопасный отказ и маловероятный крайний случай сами по себе не блокируют результат. Проверяющий revmux устанавливает факт. Проверка простоты оценивает необходимость правки.
- `P18 CONVERGENCE-CAP`. Проведи до пяти содержательных раундов revmux на статью. Авторская работа, автоматические проверки, разбор замечаний и технический повтор неполного раунда в предел не входят. При чистом результате закончи раньше. Если остались только мелкие замечания, остановись с `revmux_minor_pending`, покажи их и оставь готовность открытой. Для следующего раунда после пятого получи решение пользователя.
- `P19 SIMPLICITY-BRAKE`. Останови автоматические исправления, если правка требует более общего механизма, чем исходная проблема. Остановись также, если новый раунд выявляет проблемы преимущественно в механизме предыдущей правки. Сначала рассмотри минимальную локальную правку. Расширение объёма вынеси на отдельное решение.
- `P20 OBSERVABLE-SKILL-PASS`. Для `simplicity-spec`, `humanizer` и `simplicity-code` нужны штатный результат, хеши проверенного файла и `SKILL.md`, отдельный `run_id` назначенной роли. Независимые проверки статьи входят в обычный revmux. Для авторских проверок до revmux список исправлений не создавай. После revmux привяжи разбор к точному отчёту. Перечисли каждое принятое и отклонённое замечание. В общий список включи принятые. Даже при `clean` укажи выполненные обязательные проверки.
- `P21 CONTENT-READINESS`. До готовности статьи получи сведения и решения по всем открытым входам `researchable`, `user-decision` и `external-owner`, которые меняют требование, сценарий или AC. До ответа они остаются в `open_inputs` авторского отчёта и блокируют `ready`. Если пробел впервые обнаружил revmux, обработай его в обычном цикле замечаний. К `implementation-only` относятся только детали без влияния на наблюдаемое поведение.
- `P22 LAYER-OWNERSHIP`. Для каждой гарантии назови один ответственный слой. Укажи обязанности остальных участников. Для BE и FE опиши направление обмена, данные, событие вызова, использование ответа клиентом, серверные проверки и запрет подмены серверной проверки клиентской. Подтверди BE API, FE UI и сквозной сценарий отдельными результатами.
- `P23 COURSE-CHECK`. Когда среда напомнит о длительности хода, ведущий агент до следующего инструмента выполняет [проверку направления](course-check.md). Укажи исходный результат, текущий вопрос, новый факт, изменение границ и ближайшую проверку. После двух последовательных проверок без подтверждённого прогресса выбери `BACKTRACK`, `ASK` или `STOP` и сообщи решение пользователю. Выполни проверку в текущем задании. Для неё не нужны отдельные стадия, состояние, артефакт или агент.
- `P24 WHOLE-TO-PARTS`. До первого детального прохода подготовь полную статью по исходному шаблону. Покажи сквозные сценарии и открытые вопросы. Каждый проход по блокам начинается с полной версии и завершается новой полной версией. Сохрани прежнюю версию.
- `P25 PREANALYSIS-INTEGRITY`. В предварительной записке укажи запросы к источникам, полномочия, находки и отрицательные результаты, актуальность и покрытие. До выбора маршрута опиши проблему и последствия, цель и пользу, суть решения. Укажи, какое поведение изменится и почему это устранит проблему. Для каждого вывода укажи основание. Для истории пользователя (US) назови участника, потребность и ценность. Свяжи каждую предварительную US и каждый DoD с источником. На этапе 1 сопоставь их с итоговым текстом через `confirmed|changed|split|rejected`. Для плана нужны хеш записки, источники и проверяемые условия завершения. Назови задачу по продуктовому результату. Идентификаторы, этап и операции TRACE храни отдельно. После достаточного покрытия ищи только ответ на конкретный пробел или опровергающий вопрос.
- `P26 TRANSITION-ARCHITECTURE`. Для перехода реализации выбери `evolve-in-place|replace-and-remove|staged-migration`. Для каждого этапа укажи одного ответственного. Если есть прежний путь, укажи условия его удаления и отката. Подключи архитектора при подтверждённом [условии](architecture-analysis.md). Для проекта решения и проверки соответствия нужны разные запуски. Для намеренного отклонения запиши решение или ADR.
- `P27 DIAGRAM-GATE`. Свяжи диаграмму с конкретным вопросом, источниками и смысловыми идентификаторами. Проверь готовое изображение по [правилам диаграмм](diagram-contract.md). Требования определяет текст. До ревью автор исправляет расхождения напрямую. Замечания revmux входят в обычный список исправлений.

## Методические источники

Для постановки выбери один маршрут из `library/requirements`. Для участка разработки выбери маршрут из `library/delivery`. Если выдержки недостаточно, прочитай нужную часть полного справочника.
