# Проверка понятности и контекстной нагрузки

Проверка проведена 2 сентября 2026 года. Она отвечает на два разных вопроса:

1. уменьшился ли обязательный пакет процессной документации для одного назначения;
2. может ли независимая модель правильно применить ключевые границы нового процесса.

## Размер обязательного пакета

Сравниваются не все файлы репозитория, а типовой набор, который нужен модели для одного
назначения: entrypoint, текущий stage/flow и контракт конкретной роли. Проектные
источники и предметные артефакты в обеих системах не учитываются.

| Назначение | Старый пакет | Новый пакет | Сокращение строк | Сокращение байт |
|---|---:|---:|---:|---:|
| Предварительное планирование | 1345 строк / 122237 байт | 408 строк / 22499 байт | 69,7% | 81,6% |
| Один stage постановки | 1141 строк / 112783 байт | 365 строк / 21615 байт | 68,0% | 80,8% |
| Backend lane delivery | 547 строк / 40569 байт | 310 строк / 19312 байт | 43,3% | 52,4% |

В новый пакет дополнительно включены `process-kernel.md` и материализованный книжный
route: `scope-users`, `scenarios` или `core-change + backend-http`. Это сознательное
увеличение против первой версии замера: исходные правила Вигерса, SWEBOK и Software
Engineering at Google теперь не теряются, но загружаются выбранными sections. Остальные
stage-файлы и method routes запрещены к предварительной загрузке. Для старого пакета
использованы entrypoint, соответствующий pipeline/contract и, для planning, planning
contract. Полный старый Vigers markdown-корпус — 10798 строк; эта цифра приведена только
как верхняя граница и не используется в процентах.

Сокращение размера не доказывает качество результата, но устраняет исходную проблему:
одна роль больше не обязана держать в контексте универсальный процессный справочник.

## Независимые forward-тесты

Claude Opus запускался через `claude --safe-mode` без project instructions, skills,
plugins, hooks, MCP и custom agents. Каждый тест разрешал чтение только перечисленного
набора файлов и требовал структурированный ответ. Внешних поисков и субагентов не было.
После исправляющих diff 2 сентября повторно запущены затронутые тесты preanalysis,
delivery, diff lifecycle и method library. Первый повтор method-library честно выявил,
что разрешённый read-set не содержал точных delivery route ids. После добавления
bounded route hints второй повтор дал PASS; остальные повторы также дали PASS.

| Тест | Проверяемая граница | Результат |
|---|---|---|
| `01-preanalysis-routing.md` | полный состав предварительного анализа, порядок решений, запрет самовольной публикации | PASS |
| `02-diff-lifecycle.md` | `applied` не равно `verified`, один diff-pool, отсутствие скрытых правок | PASS |
| `03-delivery-boundary.md` | route `stop`, узкая backend ownership, разделение self-check и independent verification | PASS |
| `04-method-library.md` | выбор книжного route, project-first и запрет полной/чужой библиотеки | PASS |

Модель без дополнительных пояснений восстановила три артефакта предварительного
анализа в правильном порядке, сначала выбрала число постановок, затем режим композиции
каждой статьи и не разрешила ни агенту, ни parent публиковать план без авторизации.

Во втором тесте модель запретила переход стадии при `applied`, потребовала отдельный
`verify`, оставила ровно один defect pool и не загрузила остальные stage references.

В третьем тесте модель не запустила delivery для route `stop`, назначила
`implementation-backend` только на backend lane и не смешала developer self-check с
независимой проверкой, merge, deploy или acceptance.

В четвёртом тесте модель выбрала `requirements/scenarios` для use-case блока и
`delivery/core-change + backend-http` для backend lane, оставила проектный канон выше
общей литературы, запретила полную выжимку и basis другой lane и восстановила release
gate 70 + 30 native rules.

## Вывод и ограничение

На четырёх критичных развилках инструкции оказались однозначными для независимой модели,
а типовой процессно-методический пакет стал меньше примерно в 2,1–5,4 раза по байтам,
не потеряв адресные книжные правила. Это достаточный
smoke-check архитектуры, но не доказательство производственной эффективности.

Реальную эффективность нужно измерять на 3–5 разных задачах: сколько расхождений
переоткрывается, сколько замечаний возникает только после финальной статьи, каков
размер correction diff и сколько раундов требуется revmux. Эти метрики уже включены
в план пилота.
