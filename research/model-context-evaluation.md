# Размер пакета инструкций и проверка решений модели

Первый замер провели 2 сентября 2026 года. После переноса правил о границах решения 5 сентября обновили размеры нового пакета. Размеры старого пакета взяли из первого замера. Исследование проверяло два вопроса.

1. Сколько процессных инструкций должна прочитать модель для одного назначения?
2. Может ли независимая модель применить ключевые правила TRACE по этим инструкциям?

## Что читает одна роль

В сравнение вошли точка входа, инструкция для текущего этапа и контракт назначенной роли. Предметные материалы и проектные источники исключили из обоих замеров.

| Назначение | Старый пакет, строки / байты | Новый пакет, строки / байты | На сколько меньше строк | На сколько меньше байтов |
|---|---:|---:|---:|---:|
| Предварительное планирование | 1345 / 122237 | 528 / 32482 | 60,7% | 73,4% |
| Один этап постановки | 1141 / 112783 | 396 / 24858 | 65,3% | 69,1%¹ |
| Разработка серверной части | 547 / 40569 | 349 / 23183 | 36,2% | 42,9% |

¹ В исходном отчёте указано 69,1%. По приведённым в нём размерам сокращение составляет 78,0%: `(112783 − 24858) / 112783`. Причину расхождения замер не устанавливает.

В новый пакет включили `process-kernel.md` и выбранную часть библиотеки: `scope-users`, `scenarios` или `core-change + backend-http`. Первый замер не учитывал этот материал. Новый замер учитывает правила Вигерса, SWEBOK и Software Engineering at Google для конкретной работы. Инструкция ограничивала чтение соответствующим этапом и выбранной частью библиотеки.

В старом пакете считали точку входа и соответствующий процесс или контракт. Для планирования добавили контракт планирования. В полном корпусе Markdown Vigers было 10798 строк. Это верхняя граница. Проценты в таблице рассчитаны для отдельных назначений.

Замер показал, что роль может получить нужные правила без загрузки общего справочника. Размер пакета сам по себе не измеряет качество постановки.

## Как проверяли применение правил

Claude Opus запускали через `claude --safe-mode`. Для каждого теста задавали разрешённые файлы и формат ответа. В запусках отсутствовали инструкции проекта, скиллы, плагины, хуки, MCP, пользовательские агенты, внешний поиск и субагенты.

После исправлений 2 сентября повторили тесты предварительного анализа, разработки, состояния исправлений и библиотеки методов. Первый повтор теста библиотеки обнаружил пропуск: модель не могла прочитать точные ID маршрутов разработки. После добавления кратких подсказок второй повтор получил PASS. Остальные повторы также получили PASS.

| Тест | Что должна определить модель | Результат на дату отчёта |
|---|---|---|
| `01-preanalysis-routing.md` | Состав предварительного анализа, порядок решений и полномочия на публикацию | PASS |
| `02-diff-lifecycle.md` | Различие `applied` и `verified`, один список исправлений, проверка скрытых правок | PASS |
| `03-delivery-boundary.md` | Маршрут `stop`, ответственность за серверную часть и независимость проверки | PASS |
| `04-method-library.md` | Выбор части библиотеки, приоритет проекта и ограничение чтения | PASS |
| `05-simplicity-and-review-cap.md` | Фактический запуск проверок простоты и стиля, сохранение источников ревью, предел пяти раундов | PASS |
| `06-course-check.md` | Время проверки хода работы, решение по наблюдаемому прогрессу и полномочия после предела раундов | PASS |
| `07-solution-boundary.md` | Два противоположных риска и выбор одного из трёх горизонтов решения | UNIT-COVERED; independent run pending |

1. **Предварительный анализ.** Модель назвала три результата в правильном порядке. Сначала она выбрала число постановок. Затем определила порядок подготовки статьи и блоки для углубления. Публикация плана требовала отдельного разрешения независимо от того, кто его публикует: исполнитель или ведущий.
2. **Исправления.** При `applied` модель остановила переход к следующему этапу и потребовала отдельный `verify`. Она использовала один список дефектов и только инструкции текущего этапа.
3. **Разработка.** При `stop` модель остановилась до реализации. Она назначила `implementation-backend` только серверную часть. Проверку разработчика, независимую проверку, слияние, развёртывание и приёмку она учитывала отдельно.
4. **Библиотека методов.** Для сценария модель выбрала `requirements/scenarios`, для серверной работы — `delivery/core-change + backend-http`. Она применила правила проекта в первую очередь, исключила полную библиотеку и материал другой роли. Условие выпуска учитывало 70 + 30 исходных правил.
5. **Простота и ревью.** Модель назначила `simplicity-spec` перед предварительным отчётом и первым `revmux`, а `simplicity-code` перед независимой проверкой. Все исправления попали в текущий список. Для шестого содержательного раунда потребовалось решение пользователя. В усиленном тесте модель запросила отчёты с хешами объектов проверки для `simplicity-spec` и `humanizer`. Она отклонила чистый результат раунда, в котором отсутствовал источник `reader`. Технический повтор сбойного запуска в предел не входит.
6. **Проверка хода работы.** По напоминанию модель выбрала `CONTINUE` при подтверждённом прогрессе и доступной недорогой проверке, способной опровергнуть гипотезу. Без прогресса она исключила второй `CONTINUE` подряд. При расширении объёма она потребовала `ASK`. Отдельный этап не понадобился. Для проверки после предела раундов потребовалось явное решение пользователя. При долгом вызове инструмента проверка хода работы наступала после его завершения.

## Что установил замер

Независимая модель правильно применила инструкции в шести проверенных ситуациях. Для седьмой ситуации, выбора границ решения, на дату отчёта имелись автоматические проверки и подготовленный сценарий. Независимый запуск оставался открытым.

На типовых назначениях объём пакета в байтах уменьшился примерно в 1,7–4,5 раза. В пакете остались нужные разделы библиотеки. Для оценки работы на практике предложен пилот на 3–5 разных задачах. В нём следует измерить число повторно открытых расхождений, число замечаний, впервые обнаруженных после подготовки итоговой статьи, объём исправлений и число раундов `revmux`.
